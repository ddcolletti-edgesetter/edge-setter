# EdgeSetter Product Alignment Rules

## Product Mission

EdgeSetter exists to deliver high-quality autonomous sports intelligence for bettors, fantasy players, and sports fans. Every backend system, replay process, validation script, and API should improve the platform's ability to find, explain, calibrate, and deliver real sports edges.

## Required Product Impact

Every system must directly improve at least one of:

- Signal accuracy
- Signal speed
- Confidence calibration
- Validator trust quality
- Adversarial resistance
- Source weighting
- Historical replay accuracy
- Live alert quality
- Monetization
- Autonomous operations
- User retention
- Real-world predictive advantage

## Naming Rules

Use product-language names that make the sports intelligence purpose obvious.

Preferred translations:

- `civilization` -> `validator cluster`
- `species` -> `validator specialization profile`
- `dynasty` -> `long-horizon validator cohort`
- `governance` -> `consensus control logic`
- `extinction` -> `validator retirement/degradation`
- `promotion` -> `live-runtime eligibility`
- `reputation` -> `validator/source trust score`
- `mutation` -> `deterministic specialization adjustment`
- `survivability` -> `long-horizon signal reliability`
- `adversarial durability` -> `manipulation resistance`

## Avoided Patterns

Do not add generalized simulation infrastructure unless it has a measurable sports-intelligence output.

Avoid:

- Generalized civilization simulation
- Geopolitical systems
- Treaty, diplomacy, cold-war, sanction, empire, species, or dynasty abstractions
- Simulation for its own sake
- Infrastructure without measurable sports intelligence impact
- Naming that obscures product purpose

## Acceptance Standard

Before adding or expanding a system, answer:

1. Which product metric does this improve?
2. What sports data does it consume?
3. What user-facing or operations-facing decision does it improve?
4. How is the output validated deterministically?
5. What should be removed if this system does not prove useful?

If those answers are unclear, the system should not be added to the product path.

## Boundary Rules

Experimental infrastructure may exist only when:

- It is behind a clear boundary.
- It has no route exposure unless product-ready.
- It has deterministic validation.
- It has a documented product translation path.
- It can be deprecated or removed without affecting live signal delivery.

## Current Product Priorities

Prefer work on:

- Live feed reliability
- Odds movement and injury intelligence quality
- Source reliability and beat-writer confirmation accuracy
- Validator trust scoring from settled outcomes
- CLV and hit-rate calibration
- Alert ranking, timing, and explanation quality
- Historical replay fidelity
- Manipulation resistance for sources and consensus
- Paid-user workflows and retention loops
